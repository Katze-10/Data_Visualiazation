# 📄 SKILL: BAM-2053 Capstone Proposal (Word Document)
**Trigger:** User wants to write, improve, or structure the Capstone Project Proposal
**Output:** 600–800 word scoping document ready for submission May 25, 2026 (10%)

---

## SKILL PROTOCOL — STEP BY STEP

### STEP 1 — SCOPE CLARIFICATION (ask if not provided)

Before writing anything, confirm:
- [ ] **Topic / Dataset** — What subject? What dataset?
- [ ] **Data source** — Kaggle, Statistics Canada, open.ottawa.ca, other?
- [ ] **Team** — Solo or partner? Partner name?
- [ ] **Business question** — What problem does this dashboard solve?
- [ ] **Target audience** — Who will use this dashboard? (managers, public, analysts?)

If already provided → skip directly to STEP 2.

---

### STEP 2 — PROPOSAL STRUCTURE

Write exactly these sections (no more, no less):

```
1. Project Title (one line)
2. Team Members
3. Dataset Description (what, where, how many fields/rows)
4. Business Problem / Research Question
5. Proposed Visualizations (2-3 chart types with justification)
6. Dashboard Design Approach (layout, audience, interactivity)
7. Expected Insights / Value
```

---

### STEP 3 — DESIGN PRINCIPLES TO WEAVE IN

The proposal is NOT just a description — it must demonstrate course knowledge.
Include these explicitly or implicitly:

**Must mention:**
- Why the chosen chart types match the data type and audience (3-Lens Framework)
- How the dashboard will minimize cognitive load
- One design principle: Gestalt, visual hierarchy, or pre-attentive attributes

**Nice to include:**
- Data-Ink ratio approach (clean, minimal design)
- Accessibility consideration (color palette choice)
- Dashboard vs Report distinction (explain which and why)

---

### STEP 4 — WORD COUNT & TONE RULES

- **Total:** 600–800 words
- **Voice:** Confident student — not formal academic, not AI-sounding
- **No:** bullet-point-only sections; mix prose and structure
- **No:** copied definitions from textbooks — paraphrase and apply
- **Format for Word:** use Heading 1 for section titles, no excessive bold

---

### STEP 5 — QUALITY CHECKLIST (run before delivering)

Before presenting the proposal, verify:
- [ ] Word count between 600–800
- [ ] Topic is clearly scoped (not too broad, not trivial)
- [ ] Dataset has 10+ fields and 100+ observations mentioned
- [ ] At least 2 chart types justified with design reasoning
- [ ] Sounds like a student wrote it — not a textbook
- [ ] Topic is DIFFERENT from BAM-2024 BI Tools project

## CHART JUSTIFICATION TEMPLATES

Use these phrases to justify chart choices naturally in the proposal:

**Bar Chart:**
> "A bar chart works well here because it allows direct comparison of [X] across categories — length is processed more accurately than area, making the differences immediately apparent."

**Line Chart:**
> "To show how [metric] changes over time, a line chart is the most intuitive choice — it emphasizes continuity and trend rather than individual values."

**KPI / BAN:**
> "Key aggregate numbers (BANs) placed prominently will highlight the most critical metrics at a glance, reducing cognitive load for executive-level users."

**Scatter Plot:**
> "A scatter plot will reveal the relationship between [variable A] and [variable B], where [A] serves as the independent variable on the X-axis. We'll be careful to note that correlation does not imply causation."

**Map (Choropleth):**
> "Since the data has a geographic dimension, a choropleth map will show regional patterns using color shading — an approach that allows users to spot clusters without reading individual values."

---

## DESIGN SECTION TEMPLATE

Adapt this block for the "Dashboard Design Approach" section:

> "The dashboard will follow a clear visual hierarchy, placing KPI cards at the top for immediate overview, followed by trend charts, and detail tables at the bottom for users who need exact figures. We will use a restrained color palette — a single accent color for highlighted metrics, and neutral tones elsewhere — to reduce cognitive load and maintain focus on the data. Interactive filters (by date, region, and category) will allow the audience to drill down without cluttering the main view."

---

## COMMON MISTAKES TO AVOID IN THE PROPOSAL

| ❌ Avoid | ✅ Do Instead |
|----------|--------------|
| "We will make a nice dashboard" | Describe specific chart types and why |
| "The data has many fields" | State exact numbers: "12 fields, 500+ rows" |
| Vague audience: "everyone" | Specific audience: "regional store managers" |
| No design rationale | Link every chart to a principle |
| Over 800 words | Cut ruthlessly — quality over quantity |
| Same topic as BAM-2024 | Check and confirm topic is different |
